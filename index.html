AI Landing Zone - High Level

Hub & Spoke Architecture

Users / On-Premises

  • Enterprise apps and users reach Azure through the established hybrid network path — typically ExpressRoute or VPN into the hub VNet.
  • Traffic never needs to traverse the public internet to reach Foundry or its dependent services.
  • This is the enterprise perimeter — it stays customer-owned regardless of which VNet isolation model Foundry uses.

AI Landing Zone for APIM (Hub)

  • Centralizes access control, token governance, routing, and telemetry across every Foundry spoke.
  • Publishes API contracts — a single, governed front door for AI apps and agents.
  • Can be one deployment covering prod + non-prod, or split, depending on governance needs.
  • Enforces per-consumer token limits, semantic caching, model routing, and rate-limit-by-key policy.

AI Landing Zone for Foundry (Spoke)

  • Each business unit or use case gets its own Foundry deployment: projects, agents, models.
  • Isolation for model deployments, quotas, cost tracking, and operational ownership.
  • Templated and repeatable — new spokes onboard through infrastructure-as-code, not portal clicks.

Workload Data + Dependencies

  • Storage Account and Key Vault — included in this reference architecture; validate requirements for the selected hosting mode.
  • AI Search — grounding/RAG via Foundry IQ and agentic retrieval (usually required).
  • Cosmos DB — thread/state storage (depends on hosting pattern).
  • Private endpoints, private DNS, access permissions, and public-network restrictions must be configured together.

AI Landing Zone Blueprint

Govern once, delegate deliberately

  • Management groups organize subscriptions and inherited policy assignments. Microsoft Entra ID supplies identities; role assignments define access at the appropriate scope.
  • Policy, identity permissions, and network controls solve different problems. None substitutes for the others.

Connectivity is a shared platform capability

  • Hybrid connectivity, DNS resolution, routing, and egress controls establish approved network paths into and out of workload environments.
  • Private endpoints require working DNS and routing, supported service configuration, and appropriate public-access restrictions. Peering alone does not provide end-to-end private access.

A governed model access point

  • Applications call an APIM API, which can apply identity checks, consumer limits, backend selection, and diagnostics before forwarding a model request.
  • The gateway is a logical shared service. Its subscription and network placement depend on the APIM tier and enterprise topology; it need not reside inside the connectivity hub.
  • The arrows show a conceptual application-to-gateway-to-model request. They do not imply that every tool call or retrieval operation passes through APIM.

The application owns the user-facing workflow

  • Application orchestration assembles prompts, retrieves authorized context, and controls which tools or actions may run.
  • Document permissions and approval for high-impact actions belong in the application design, not merely in a network diagram.

A repeatable environment for AI workloads

  • Foundry projects organize AI development and access to model and agent capabilities. The workload team owns evaluations, releases, and operational readiness.
  • Separate subscriptions, resources, projects, or environments according to the required isolation boundary. A project is not automatically a separate network or subscription boundary.

Dependencies follow the use case

  • A model-only application may need no search index. Retrieval adds governed data access; stateful agents and tools introduce their own runtime and storage requirements.
  • Search, storage, state stores, and secrets services are examples, not a mandatory bundle. Both applications and agent runtimes may access these dependencies.

Operate the platform and workload together

  • Correlate gateway, application, and model diagnostics while protecting prompt and response data. Define retention, access, and incident ownership.
  • Use infrastructure as code for repeatable environments. Assign budgets and cost ownership; budget alerts alone do not stop spending.

Microsoft-Managed vs. Customer-Managed VNet

Microsoft-Managed VNet

  • Microsoft handles subnet range, IP selection, and delegation — fastest path to private connectivity.
  • Storage and Search isolation supported out of the box via managed private endpoints.
  • Lower operational burden — no firewall, UDRs, or peering to design and maintain.
  • Trade-off: customer-controlled routing and inspection are constrained. Validate connectivity and diagnostics support for the selected service and deployment mode.

Customer-Managed VNet (BYO)

  • Full control: your own Azure Firewall/NVA, user-defined routes, and network peering.
  • Connects to hub/spoke, shared services, or on-premises via ExpressRoute/VPN.
  • Encryption key ownership is a separate service-level decision, not a property of a private endpoint.
  • Trade-off: more complex setup (subnet delegation to Container Apps, CapHost creation), private IP ranges only, /27 minimum subnet for agent delegation.
Network design decision: private connectivity alone does not require a customer-managed runtime VNet. Evaluate BYO when you need customer-controlled routing, inspection, or integration with existing networks. Confirm supported inbound and outbound paths for the selected Foundry service and deployment mode. The enterprise perimeter remains a separate responsibility.

AI Landing Zones in Detail

Apps & Agents (Consumers)

  • Every AI app or agent in the estate calls through the same governed door — no direct-to-model access.
  • Consumers are identified by subscription key or Entra identity, never by a shared secret baked into code.

APIM Gateway

  • Centralizes access control, token governance, routing, and telemetry across every Foundry spoke.
  • Publishes API contracts — a single, governed front door for AI apps and agents.
  • Can be one deployment covering prod + non-prod, or split, depending on governance needs.
  • Enforces per-consumer token limits, semantic caching, model routing, and rate-limit-by-key policy.

Foundry Spokes

  • The hub fans out to every Foundry spoke — one per business unit, product, or use case.
  • New spokes plug into the same gateway contract without renegotiating access for every consumer.

Shared Services

  • One Log Analytics workspace per environment tier makes cross-service audit joins possible.
  • Key Vault holds gateway certificates and secrets; Entra ID backs every identity check at the gateway.
